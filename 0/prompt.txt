## 1. What it is

- Pi Durable is an experimental harness framework for long-running, durable agents that run anywhere there is a JavaScript runtime. The announcement says it "does not replace the Pi coding agent". It is a framework for building any agentic application, coding agents included. (docs: https://earendil.com/posts/pi-durable/ and https://earendil.com/posts/pi-1-0/)
- Version: 1.6.0, released 2026-11-20 (npm registry, https://registry.npmjs.org/@earendil-works/pi-durable). It is MIT licensed and the repo was pushed on 2026-11-23. The README says "Experimental. The API changes without notice between releases." (source: https://github.com/earendil-works/pi/tree/main/packages/durable)
- Pi packages it reuses:
  - It depends on `@earendil-works/pi-ai` for model access, which is the same package the coding agent uses.
  - It depends on `@earendil-works/chord` (document state and operations), `pi-schema`, `pi-codemode` and `pi-telemetry`.
  - The announcement says it shares the coding agent's TUI components in the demos.
- What it replaces or bypasses: the package list has no `pi-agent-core`. Durable has its own `Harness`, task scheduler and storage layer. It ships its own read, write, edit and bash tools (`CodingTools`). The announcement shows no use of `pi-coding-agent`; its demos live inside that package under `experimental/`, borrowing its TUI.

## 2. Architecture

- **Terms** (announcement):
  - Harness: storage plus the machinery to run conversations in parallel.
  - Conversation: a transcript of immutable entries.
  - Agent: a model plus its settings and tools.
  - Task: everything the harness runs, from model calls to tool calls.
  - Execution environment: where tools do their work.
- **Where the loop runs.** In the process that owns the storage. "One process owns a storage at a time, and other clients attach to that process." There is no cross-process locking (README, Storage). Read-only viewers can open the same storage with `readOnly: true`.
- **State and persistence.**
  - Every change goes through atomic commits. Nothing is shown before its commit is stored. A commit can write entries, documents and tasks together.
  - Documents are typed JSON next to the transcript. Built-in documents are `pi.agent`, `pi.live`, `pi.inbox`, `pi.usage` and `pi.provider`.
  - Storage backends are memory, IndexedDB, SQLite, JSONL and a Cloudflare Durable Object SQLite backend.
  - SQLite uses WAL with `synchronous = NORMAL`. Commits survive process crashes, but the newest may be lost on power or host failure.
  - JSONL keeps the whole history in memory, so the README says to use SQLite for long-running agents.
  - Older messages always stay in storage, even after compaction.
- **Crash recovery.**
  - Each task is a durable state machine that saves a checkpoint at every step. A new process opens the storage, finds unfinished tasks and calls `harness.resume()`.
  - A cut-off model request is re-sent, and the partial answer stays in the transcript marked aborted. A request that keeps killing the process eventually ends.
  - A cut-off tool call reruns only if the tool declares `replay: "safe"`. Otherwise the model is told the call was interrupted, along with the output stored so far.
  - A `requestId` on a submission makes it exactly-once.
  - Hooks that make decisions store them in a `memo`, where the first write wins.
- **Tool execution.**
  - Each tool call is its own task, and its intent is stored before it runs.
  - Tools reach files and shell through an `ExecutionEnv`. The `env` function runs per tool call, so each conversation can use a different directory, container, remote VM or in-memory sandbox.
  - Shipped: `NodeExecutionEnv` for local files. The README mentions pi-env's `RemoteExecutionEnv` and `LocalExecutionEnv`.
  - Codemode runs model-written JavaScript in a QuickJS sandbox (`pi-codemode`) that can also resume after a restart. On Cloudflare you pass a `RemoteCodemodeSandbox`.
  - The README does not document a built-in permission or approval system. The announcement shows an approval hook written as an extension (blocks `deploy`, asks in Slack).
- **Client connection.**
  - `conversation.watch()` returns the current view first, then each commit as Chord operations. These are "small enough to send over a socket", and you wire the transport yourself.
  - `watchEvents()` converts commits into the coding agent's event shapes, at the cost of more bytes on the wire.
  - The view holds a window of the newest 50 entries. `ConversationTranscript` handles reconnects and "load earlier".
  - A late-joining or reconnecting client starts from the current view.
  - I found no standard wire protocol. The Cloudflare example defines its own in `src/protocol.ts`.
- **Background and long-running work.**
  - Tasks are foreground by default, so Esc or an abort stops them and everything they own.
  - A background task (`ownership: { kind: "conversation" }, background: true`) lets the conversation go idle while it runs, and an ordinary abort leaves it alone. The announcement gives a subagent and a reminder that fires tomorrow as examples.
  - Tasks and conversations form one ownership tree, and aborts run bottom-up.
  - Sleeps are stored (`runtime.sleepUntil`) and hold no invocation while waiting.
  - Compaction is a task that runs in the background while the conversation continues. `reset()` and handoff start a new context.
  - Subagents are not built in. A tool creates a child conversation it owns.
- **Multiple clients and conversations.**
  - Any number of clients can attach to any conversation, and any client can steer.
  - Submitting to a busy conversation queues it in `pi.inbox`. `whenBusy: "steer"` joins the running work after the current tool round. A follow-up starts the next run.
  - One harness runs many conversations concurrently. A conversation can fork at any entry and sees the parent's history without copying it.

## 3. Differences from pi-coding-agent

The coding-agent side comes from https://github.com/earendil-works/pi/tree/main/packages/coding-agent and the Pi 1.0 post. I did not re-verify the JSONL session tree or the four-tool default in the coding-agent docs, so those items are your premise, not confirmed here.

| Aspect | Pi coding agent | Pi Durable (source) |
|---|---|---|
| Process model | "Runs on your (remote) machine, inside a terminal, driven by one person. If the process dies, you look at what happened and tell it to continue." | Process death is resumed automatically from checkpoints. Multiple humans can steer the same agents. |
| Session state | Your premise: JSONL tree | Entries, documents and tasks in pluggable storage (SQLite, Durable Object, etc.) with atomic commits. JSONL is one optional backend. Forks share parent history. |

## 4. Stated trade-offs

- **Gains** (announcement): runs anywhere, long conversations through compaction, crash survival, multi-client steering, and malleability. The source is about 15,000 lines without tests, which Earendil gives as about 150k to 250k tokens, so an agent can read it.
- **Costs and limits** (stated):
  - It is experimental and the API may change.
  - One process owns a storage, with no cross-process locking.
  - Recovery re-sends cut-off model requests, which costs tokens.
  - Non-idempotent tools must be written with replay semantics in mind. A tool without `replay: "safe"` is never rerun after a crash.
  - A phase reruns from its top after a restart, so work after a wait must go in the next phase.
  - SQLite can lose the newest commits on power or host failure.
  - The `watchEvents()` compatibility layer costs more bytes than operations.
  - Storage conformance suites and benchmarks ship in the package, but I found no published latency numbers.
- **Not documented:** latency overhead, a security or permission model, and infrastructure cost comparisons. The announcement does not name them as trade-offs. The Cloudflare sample says it has "no authentication or rate limiting" and warns to add both before exposing a deployment.

## 5. Cloudflare deployment

Source: https://github.com/earendil-works/pi-durable-cloudflare, repo pushed 2026-11-10, depends on pi-durable 1.5.2.

- Clients connect over Cloudflare hibernating WebSockets. Each socket watches one conversation, receiving a first value and then Chord operations. A React client applies them. Each connection is tagged with a username for multiplayer.

## 1. Lifecycle of a model request task and a tool call task

**Model request: `pi.generation`** (spec §8.3, https://github.com/earendil-works/pi/blob/main/packages/durable/docs/spec.md; version 3)

The checkpoint phases are `prepare` (initial, `{phase:"prepare", attempt:1}`), `request`, `retry`, `poll`, `tools`, `finish`, `drain`, `afterTools` and `yield`.

- **`prepare`**
  - One commit appends the planned `pi.system` entries and moves to `request`.
  - The checkpoint then holds model, thinkingLevel, streamOptions and `cutoff` (the newest entry included in the request).
  - Resume: it runs again from the top.
- **`request`**
  - Before the call, `pi.live.generation` is set (attempt number) by a deferred commit.
  - Partial output is committed as `pi.live.generation.message`, throttled to every 100 ms by default. These commits are deferred: watches see them at once, and storage gets them with the next commit that reads `pi.live`, or within `persistWithinMs` (default 1000 ms).
  - The terminal message is classified in one commit that also clears the partial.
    - `stop`/`length` appends the `pi.assistant` entry.
    - `toolUse` appends the assistant entry and starts the tool round, moving to `tools`.
    - A retryable `error` appends the error entry and sleeps at `retry`.
    - A deferred response sleeps at `poll`.
    - Any other error, or `aborted` without an abort mark, appends the error entry and fails the task.
  - Resume after a close: the request is re-sent with the same committed messages, model, thinking level and stream options, and `beforeRequest` runs again.
  - Resume after a crash (the record's `restarts` &gt; 0):
    - A leftover stored partial is first converted into an `aborted` `pi.assistant` entry.
    - The attempt counts as failed. If the retry policy allows it, the task sleeps at `retry`, with the note "The host stopped while the model was answering, on attempt N".
    - Otherwise the run ends `interrupted`.
    - It is not re-sent immediately. After `restartLimit` crashes the run ends `restart_limit`.
  - A crash before the first store leaves no aborted entry, and that attempt's usage is not recorded.
- **`retry`**: waits until `until`, then returns to `prepare` with the next attempt. If run before `until`, it sleeps again.
- **`poll`**
  - The checkpoint holds the deferred `handle` and `pollAt`.
  - On resume after a crash, a fetch that was in flight is charged as a failed attempt, but the deferred response is polled again instead of re-requesting.
- **`tools`**: the task waits (`waiting` status, `allSettled`) on the round's tool tasks.
- **`finish`, `drain`, `afterTools`, `yield`**: these are about hooks that run after a round or after the answer (afterRun, afterTools and onYield tasks). The abort and restart-limit rules for these phases are in spec §8.3.

**Tool call: `pi.tool`** (spec §8.4; version 4)

The checkpoint phases are `call` (initial), `execute` and `parked`. The spec comments `execute` as "Intent: `execute()` runs in the phase that commits it; reached as a phase only by recovery."

- **`call`**
  - It validates the arguments and runs the `beforeTool` chain.
  - A deferred commit sets the slot in `pi.live.tools` to `running`.
  - One commit then records intent: it moves to `execute` with the final arguments and `replay: "safe" | "unsafe"`.
  - `execute()` runs in the same handler, then `afterTool` runs.
  - The result commit appends one `pi.tool-result` entry, marks the slot `done` and completes with `{entryId, control}`.
  - A tool that does not resolve, invalid arguments, or a block commit an error result with no intent.
- **Partial output**
  - Running output lives in the slot (`output`, `details`, `diagnostics`) as throttled, deferred commits (default 100 ms).
  - Each run of `execute()` starts with empty output.
- **`execute`** (reached only by recovery)
  - If the stored and the current policy are both `safe`, it executes again with the stored arguments, wake and checkpoint, without `beforeTool`.
  - Otherwise it commits an `interrupted` error result built from the durable partial output, and the task ends `failed`. If the run had been woken from a park, `cancel` runs first. The README says the same: "reruns on reopen only when it is declared `replay: "safe"`; otherwise the model gets an `interrupted` error result with the output committed so far."
  - A close and a crash both leave `execute`, so a replay-unsafe run is never repeated.
  - After `restartLimit` cut-offs it commits a `restart_limit` error result instead.
- **`parked`**
  - A tool can return a park (`sleeping` or `waiting`). One commit stores the latest details and diagnostics and the `parked` checkpoint.
  - The `parked` handler runs when the park is woken. It commits intent (`execute` with the wake and checkpoint) and runs `execute()` again.
  - A restart while parked runs no tool code (README line 426).
- **Abort**: for `parked`, or `execute` with a wake, `cancel` runs first. An `aborted` error result is then committed from the slot's durable partial output.

**Shared pattern:** spec §5.2 "Effect sandwich" is "commit intent phase / perform external effect / commit outcome or next phase". Its rule is that "Reopening in an intent phase means the effect may have happened."

The word "safe" is a tool's `replay` field. "Interrupted notice" is the result the model gets in the transcript.

## 2. Commit, entries, tasks, documents

Spec §1 states the core rule: "A Session atomically commits immutable entries, full task records, and Chord-tracked documents. Only committed state is observable."

- An entry (`EntryRecord`) is an immutable transcript record in one conversation. Its fields are `id`, `conversationId`, `kind`, optional `model` (messages), `data`, `head`, `edits` and `byTaskId`. Entry ids are Session-global, ordered and never reused.
- A task is a durable state machine, stored as a `TaskRecord` holding its input, a checkpoint and a state (`pending`, `running`, `waiting`, `sleeping`, `completing`, `terminal`).
- Memos are small JSON values inside the live task record.
- A document is mutable JSON, stored as one base plus later deltas (Chord ops).
- The storage layer (§10) takes a commit as a batch of writes: `conversation`, `entry`, `task`, `submission`, `document.create`, `document.copy`, `document.change` and `document.retire`. All are atomic with one `seq`. The mutation line runs one commit callback at a time, and storage writes are group-committed.
- Deferred commits may touch only existing conversation documents. They are visible to watchers before they are stored, and a crash loses them.
- A terminal task transition writes the terminal record, appends result entries, retires the task's documents and settles submissions in one commit (§5.3).

## 3. defineTask, sleepUntil, signals

- **`defineTask`** (§5.1): the definition is `{name, version, initial(input), phases, abort, migrate?, hooks?}`. `phases` is a handler per `phase` value in the checkpoint. A phase handler ends by calling `runtime.commit(...)` with the next state: `running` with a new checkpoint, `waiting`, `sleeping` or `terminal`. After a crash or close, a phase reruns from its top. `abort` is the handler for aborts.
- **`runtime.sleepUntil(until, checkpoint, context)`** (§5.6): it commits a sleep and resolves when the sleep is stored. The phase then returns, and the task resumes at the checkpoint once the Harness clock (`HarnessOptions.now`, epoch ms) reaches `until`. Deadlines survive reopens. The spec says "There is no sleep inside a phase", so work after the wait goes in the next phase. Work before the sleep is not exactly-once.
- **Signals** (§5.7): `defineSignal({name, version, schema})` gives a token, and `token.key("k")` names one wait.
  - A task sleeps with `{status:"sleeping", signals:[...], until?}`.
  - `harness.signal()` or `tx.signal()` delivers a value, with result `delivered`, `duplicate`, `invalid`, `closed` or `not_found`.
  - The value is stored in the task's memos as `pi.signal.&lt;name&gt;/&lt;key&gt;`. A value delivered early is kept.
  - On wake, `runtime.readSignal` returns `{kind:"value"}` or `{kind:"expired"}`.
  - The wake reason is `time`, `expired`, `signal` or `tasks`. Each key can wake a task only once.

- **Interface:** `ExecutionEnv extends FileSystem, Shell` (`packages/durable/src/env/index.ts`, `@earendil-works/pi-durable/env`).

- **Can the env change between tool calls?** Yes, per the README and spec, both documentation:
  - `HarnessOptions.env(target)` receives `{conversationId, cwd, read}`. README: "builds the execution environment for each tool call".
  - A tool's `api.env` is built right before executing (§8.4). A fresh object per call is fine.
  - `edit` and `write` serialize per env `id` and path, so equal ids must mean the same files.
  - A throw from `env` becomes the call's error result.
  - Because the function runs per call and receives `read`, an app can return a different env (different `cwd` or container) on a later call. The docs say "one container per conversation" is the intended use but do not describe switching mid-conversation. I did not run a trial.

## 6. watch and submit

- **`conversation.watch(context, window?)`** (README §Watching a Conversation, spec §9.3) returns a watch.
  - `watch.value` is the view at attachment. `watch.start(listener)` receives `{kind:"value", value, ops, retired}` calls.
  - `stop()` and `closed` give a `WatchEnd`: `stopped`, `aborted`, `ended`, `listener_error` or `failed`.
  - The window is `{from?, min=50, max=2*min}`.
  - Related methods:
    - `harness.observeConversation`, `observeTaskGraph` and `observeDoc`: synchronous observers with `advance` and `detach`.
    - `ConversationTranscript` helpers: `merge`, `loadEarlier`, `fillGap`, `resume`.
    - `conversation.entries()`: paged scans.
- **`watchEvents()`:** I found no such name in the README, the spec, `packages/coding-agent/docs/sdk.md` or `packages/durable/src/env`. I did not search the rest of the repository.
- **`submit(draft, context)`:**
  - `type:"input"` takes `content`, `whenBusy?: "steer" | "followUp" | "reject"`, `whenIdle?: "reject"`, `onAbort?: "withdraw" | "keep"`, `requestId?` and `notify?`.
  - `type:"write"` takes `entry`. `type:"continue"` takes nothing.
  - The default `whenBusy` is follow-up.
  - `"reject"` throws `ConversationBusy`; `whenIdle:"reject"` throws `ConversationIdle`.
  - Steers are placed after the current tool round. Follow-ups are placed when the run answers and start the next run.
  - Related methods: `admit(tx, draft)` (the same admission inside your own commit), `submission.wait()`, `submission.abort(context)`, `harness.submission(id)`.
  - The same `requestId` returns the same submission.
- **What a late client receives:**
  - The README says "A client that joins late or reconnects starts from the current view; nothing is replayed."
  - That view is the newest 50 entries plus `pi.live`, `pi.inbox`, `pi.usage`, `pi.agent` and `pi.provider`, including the in-progress partial.
  - With `from`, it gets entries after that id. If more than 10,000 ops are pending, a client gets one root replacement `[["r", view]]`.
