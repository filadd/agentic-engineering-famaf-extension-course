# kurasu: web rules

verified: 2026-10-22

Answers how kurasu's web is built: how screens share pieces, how they reach the API and where files go.

## Knowledge

- A piece used by both the student and the teacher is one component. The common part is inside it, and what each side adds enters through slots: a `ReactNode` prop for a fixed place, or a function that receives the row (`renderActions`, `renderHand`) for a per-row place. There is no admin flag.
- In program designs, slots follow the notation of the plugin's `component-tree` reference: `<slot>`.
- API access follows the wiki entry `tanstack-query/operation-hooks`: one hook per operation in `apps/web/src/features/<topic>/<hook>.ts`, keys from `queryKeys`, and typed `options` passed through. Each operation hook is built on `useApiQuery` or `useApiMutation` (`apps/web/src/api/`), which call `runApi` with the Effect HttpApi client. A screen never calls `useQuery` or `useMutation` directly. A query whose `queryOptions` are shared with a non-hook caller calls `useQuery` over those options instead: `useMaterialFile` (shared with the slides check).
- An operation hook does not list its errors by hand. Its `options` take `EndpointError<"group", "endpoint">` (`apps/web/src/api/api-error.ts`), which reads the error type of that endpoint from the HttpApi client: the endpoint's own errors, its middleware's (`Unauthenticated`, `NoAccess`, `NotTeacher`), `HttpClientError` and `SchemaError`. `useApiQuery` and `useApiMutation` infer the error type from `call` too, so options that name another endpoint's errors fail to typecheck. An endpoint without the login middleware, such as `auth.requestLink`, has no `Unauthenticated` in its errors.
- `useApiMutation` runs the hook's own callbacks before the screen's, and invalidates its `invalidates` keys before the screen's `onSuccess`, so the screen always sees fresh data.
- An instant action passes `optimistic` to `useApiMutation`: a list of entries built with `optimisticPatch({ key, exact?, patch })` (`api/optimistic-patch.ts`). `key` is a function of the input, because some keys name one record, such as one session. `exact` is for a key that is a prefix of other keys holding another data type. The mutation cancels and snapshots those keys, patches them before the request, puts the snapshot back on failure and invalidates after a failure too.
- A mutation's `errorToast` is a function of the input that returns the toast text, or `undefined` for no toast (a word cloud vote shows its error inline instead). An access error shows no toast; the query client sends the user to the login instead.
- The toast comes from sonner. `<Toaster>` is mounted in `__root`, and `showError(text)` and `showSuccess(text)` in `ui/toast.ts` call `toast.custom` with the shared `ui/Toast`, whose `variant` sets the icon and the role: `error` is an alert with the danger icon, `success` a status with the check. They are plain functions so a hook's `onError` or `onSuccess` can call them. `test/setup.ts` calls `toast.dismiss()` after each test, because sonner keeps its toasts in module state outside the rendered tree and one test's toast would show up in the next.
- Loading: a part that reads data renders `data == null ? <SkeletonOf>…</SkeletonOf> : …`. `ui/SkeletonOf` wraps the real part filled with example data, kept per topic in `features/<topic>/*-examples.ts`, so the skeleton takes the part's own size. Skeletons are coarse: wrap a whole card (the highlighted session, each card of a folding section, each poll card, each list row, the slide, the header's name and avatar), never the inside of one. `.skeleton` paints the wrapped card as one soft grey block in the theme's colours and hides everything inside it, text, buttons and icons included. It adds the `.skeleton` class, `inert` and `aria-hidden`. It adds `aria-hidden` as well as `inert` because Testing Library ignores `inert`, and a screen reader must not read the example data.
- The login check does not block the page. `useMe` is built on `useApiQuery`, and components do the redirects: `_app` renders `<Navigate to="/setup">` for an incomplete profile, and the query client sends the user to the login on an access error.
- A query throws to the error boundary only when it has no data and the error is not an access error (`throwOnError` in `api/create-query-client.ts`); a failed refetch keeps the data already on screen. The router's `defaultErrorComponent` is `ui/ErrorScreen`, whose "Volver al inicio" calls `queryClient.resetQueries` on the queries in error before navigating home. Resetting React Query's error boundary is not enough: the reset lasts only until the first query mounts, so a page reached through a redirect, such as the teacher's `/admin` after `/`, mounts its query still in error and throws again.
- A query that only one role may run waits for the role with `enabled`. The API answers the other role with a 403, `NotStudent` or `NotTeacher`, which is not an access error. When the screen has no data yet, `throwOnError` sends that 403 to the error screen. On `/`, the student's sessions and active polls pass `enabled: me.data?.role === "student"`, so they wait for `me`, and the page draws the student's skeleton meanwhile.
- `ui/Button` is the only text button, with variants `main`, `pill`, `pill-dark` and `pill-danger`, and a `pending` prop with an optional `pendingLabel`. A pending button is disabled, shows a spinner and keeps its full colour. `Button` renders only a `<button>`. A link styled as a button is `ui/ButtonLink`, with the same variants and `to`/`params` typed per route as in the router's `Link`. `ButtonLink` renders the router's `Link`, so it navigates inside the app. Icon buttons (`icon-button`) stay outside both.
- The upload dialog and the material list check an HTML marked as slides with the same `useSlidesCheck` (`features/materials/`), and show its state with `SlidesCheckNotice`. The hook loads the HTML in a hidden `SlidesFrame` that the caller renders from `frame`. It shows the result no earlier than one second after `start`, so a fast check does not show and hide its notice at once. The list passes `okFor: 10_000`, so its ok notice goes away after 10 s; the dialog passes no `okFor`, so its ok notice has no time limit.
- `useClassroom` handles live classroom updates. Each WebSocket notice invalidates the keys of its topic, and data always comes through the hooks.
- Confirmations and overlays use the shared pieces in `ui/`. `ConfirmAction` holds the dialog's state (closed, asking, confirming, failed), takes a `renderTrigger`, an `onConfirm` and an `errorText`, and wraps `ConfirmDialog`. The dialog closes when `onConfirm` resolves and stays open with `errorText` when `onConfirm` rejects. `ConfirmDialog` takes `pending`, `pendingLabel` and `error`; while pending, Cancelar is disabled and neither Escape nor a click outside closes it. `Backdrop` draws the background of a sheet, an alert or the projected view, and closes on a click outside its content and on Escape.
- Escape closes only the topmost open backdrop. `useCloseOnEscape` keeps one shared stack of closers and one `keydown` listener; with one listener per backdrop, Escape would also close the sheet under a confirmation. The browser runs microtasks between listeners, so by the time the sheet's listener runs, the confirmation is gone and the sheet is on top.
- Folders follow the topic, not the file kind: `features/<topic>/` holds a topic's components and hooks together. Browser state helpers go in `helpers/` (`helpers/local-ui/`), shared UI in `ui/`.
- Each file holds one component or hook, and uses named exports.
- Styles use Tailwind 4; the prototypes' colours and dark mode live in the theme.
- Repeated styles are classes in `@layer components` of `styles.css` (`main-button`, `pill-button`, `input-field`, `paper`, …). A class name must not match a utility Tailwind generates from a theme colour: a `.text-field` class got the `text-field` utility generated from `--color-field` as well, which painted the input's text white on a white field. The input class is `.input-field`.
- The UI is in Spanish; code is in English.
