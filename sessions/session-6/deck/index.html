# ¿Qué son los pesos?

  • Un LLM es como una consola de sonido con miles de millones de perillas. Antes de entrenar, están casi al azar
  • Entrenar: pasar datos, medir el error de la predicción, mover las perillas, y repetir muchísimas veces
  • Los pesos son los valores aprendidos, guardados como tensores: arreglos multidimensionales de números
  • 8B, 30B = miles de millones de parámetros, casi todos pesos. Los modelos frontera: cientos de miles de millones, o billones

# La arquitectura y los pesos son cosas distintas

arquitectura — capas, conexiones, mecanismo de atención, el camino de los datos

pesos — los números aprendidos puestos dentro de esa arquitectura

runtime — el software que carga las dos cosas y calcula respuestas

Una API esconde todo esto detrás de un request HTTP. Un release open-weight te deja traer las piezas a tu máquina.

# ¿Qué significa open-weight?

Un modelo open-weight es uno cuyos pesos aprendidos se pueden descargar.
Qué podés hacer con ellos lo decide la licencia.

el ejemplo del post

Muse Glimmer — Meta, agosto 2026. 30B parámetros, pensado para agentes locales: lee texto e imágenes, llama tools y se recupera cuando una tool falla.

Meta lo publicó bajo Apache 2.0, una licencia permisiva.

la definición de la OSI

La Open Source AI Definition pide más que los parámetros finales: el código para entrenar y correr el sistema, e información suficiente sobre los datos de entrenamiento como para recrearlo sustancialmente.

El límite se sigue discutiendo. Cuando una empresa publica los parámetros sin todo lo que usó para crearlos, “open weight” es el término preciso.

# Por qué importa la quantization

# los pesos ocupan mucha memoria
30 mil millones × 16 bits ÷ 8 = 60 GB
# quantization: guardarlos con menos bits
30 mil millones ×  4 bits ÷ 8 = 15 GB
      .-'''''''''''-.
    .'       8       '.
   /                   \
  ;                     ;
  | 16       ●══════4   |
  '---------------------'
      bits por peso
16-bit ████████████████████████████████████████████████████████████ 60 GB
~4-bit ███████████████                                              15 GB
  • + archivo más chico, menos memoria, puede correr más rápido
  • − menos precisión: puede cambiar la calidad. Los buenos métodos conservan más de lo que sugiere la cuenta de bits, pero probá ese modelo y esa cuantización en tu tarea

Las cuantizaciones de la comunidad aparecen rápido: un release pensado para GPUs de datacenter suele estar en días en formatos para Apple silicon, GPUs de consumo o CPU.

# Qué te permiten los open weights

01Fijar la versión

El proveedor puede actualizar, cambiar el precio o retirar un modelo. Con los pesos bajados, tu app no cambia en silencio.

02Datos en tu máquina

Notas, código, registros de clientes. Pero local no es automáticamente privado: el agente puede llamar APIs, subir archivos o escribir logs. Revisá todo el flujo.

03Elegir quién lo corre

Comparar precio, velocidad, ubicación y confiabilidad. Ej.: GLM-5.3 en la app ZCode, vía la API de Z.ai en Claude Code, o en tu GPU con vLLM.

04Fine-tune

Terminología de la empresa, un framework interno, un estilo, clasificar tickets, un idioma flojo. Full fine-tuning es caro; LoRA entrena un set chico de parámetros agregados.

05Estudiarlo y probarlo

Inspeccionar activaciones, sacar o reemplazar capas, comparar cuantizaciones. La comunidad lo porta a hardware que el creador nunca probó.

06Modelos chicos como piezas

Clasificar, extraer campos, resumir documentos privados, un paso de un sistema mayor. No tiene que ganar todos los benchmarks: tiene que hacer una tarea de forma confiable.

# La licencia importa tanto como la descarga

Todo modelo tiene una licencia o términos de uso. Que se pueda bajar no significa que lo puedas usar para cualquier cosa.

Antes de construir encima, chequeá si permite:

[ ] uso comercial
[ ] redistribuir pesos originales o modificados
[ ] ofrecerlo como servicio hosteado
[ ] fine-tune, cuantizar, convertir formatos
[ ] uso por encima de cierto tamaño de empresa
    o cantidad de usuarios
[ ] uso en industrias o aplicaciones puntuales

Algunas familias usan licencias conocidas como Apache 2.0; otras, licencias propias con restricciones extra.

“Está en Hugging Face” no dice nada de los términos legales.

Bajan la memoria que necesita.

# Lo que los open weights no te garantizan

  • Buena calidad de salida
  • Respuestas correctas
  • Datos sin sesgo
  • Hardware barato
  • Generación rápida en tu máquina
  • Permiso para usarlo como quieras
  • Info para reproducir el entrenamiento
    _________________
   ╱  open-weights  ╱│
  ┌────────────────┐ │
  │ 0.73 -0.02 1.2 │ │
  │ -0.65 0.44 ... │ │
  │                │╱
  └────────────────┘
  garantías: no incluidas
≠ barato

Almacenamiento, memoria de inferencia y contexto largo cuestan. Tráfico alto = más GPUs. Alguien tiene que operarlo.

Para un modelo gigante, una API hosteada puede salir mucho más barata.

Contá hardware, energía, horas de ingeniería, observabilidad, escalado, failover, seguridad y actualizaciones — no solo el precio por token.

≠ seguro

Self-hosting te hace el operador: elegís runtime, asegurás la máquina, actualizás, medís calidad, decidís a qué accede.

No elimina las alucinaciones. Un agente local puede borrar un archivo, exponer un secreto o seguir una instrucción maliciosa.

El riesgo es modelo + tools + permisos amplios + poca revisión, corra donde corra.

# Cómo usaría un modelo open-weight

El autor no reemplazaría todos los modelos en la nube por uno local.

empezar por

Tareas chicas y frecuentes, donde la privacidad y un costo predecible importan más que el razonamiento de frontera.

evitar uno local cuando
  • tu hardware no lo corre cómodo
  • unas pocas llamadas a una API cuestan menos que el hardware
  • la tarea necesita el mejor razonamiento disponible

# Cómo evaluar un modelo open-weight (1/2)

Diez chequeos antes de bajarlo:

  1. ¿Lo puedo bajar hoy? Un release futuro sigue siendo una promesa.
  2. Licencia. ¿Puedo usarlo, modificarlo y redistribuirlo en mi proyecto?
  3. Cantidad de parámetros. Suficiente para la tarea y chico para mi máquina. Totales y activos no son lo mismo.
  4. Quantization. Qué versiones hay, cuánta memoria necesita cada una y cuánta calidad pierde.
  5. Soporte de runtime. ¿Son públicos el tokenizer, la configuración y el código de inferencia? ¿Anda en Ollama, llama.cpp, MLX, Transformers o en mi servidor?

# Cómo evaluar un modelo open-weight (2/2)

  1. ¿Base o instruct? Un modelo base puede necesitar más entrenamiento para comportarse como asistente de chat.
  2. Largo de contexto. ¿Entra el input de mi tarea? ¿Cuánta memoria extra usa ese contexto?
  3. Model card. Uso previsto, entrenamiento y evaluación, y las limitaciones que declara.
  4. Benchmarks reproducibles. Un puntaje sin el mismo harness, prompts y tools es difícil de comparar.
  5. Tu propio set de pruebas. ¿Funciona con ejemplos reales de tu aplicación?
No elijas solo por un leaderboard. El mejor modelo es el más chico que hace tu tarea suficientemente bien, en hardware que puedas correr.

# Para llevarse

+ pesos = resultado del entrenamiento, no el código ni los datos
+ open-weight ≠ open source
+ la licencia decide qué podés hacer — y cambia entre modelos de una misma familia
+ 30B × 4 bits ÷ 8 ≈ 15 GB: la quantization (o cuantización) decide si entra en tu máquina
+ abierto ≠ accesible: un 2.8T requiere hardware muy potente, que no es de simple acceso
+ local ≠ barato, ≠ seguro: el operador sos vos
+ elegí con tu propio set de pruebas, no con un leaderboard
- “modelo abierto” como categoría útil
