# Session 2 — Planning & Review (Instructor Notes)

> Owner: Agus. Status: shaping. Audience-facing materials live alongside this file (slides.md, exercise/README.md) and are in Spanish. These notes are for the instructor in English.

## Session goal (in one sentence)

Students leave knowing how to **externalize a plan and review a diff before accepting** — internalizing "don't accept what you didn't externalize and didn't review."

## Audience & assumptions

- **This session is 2 hours.** Session 1 was 3; the extra hour there bought the introductions and the Pi install. There is no setup hour here — protect the hands-on block.
- Heterogeneous — 1st year through graduates. Teach to the middle, with entry points for beginners and depth for advanced students.
- **Git baseline**: assume basics (commit/push). Teach diff-reading critically and branching-as-safety-net with AI explicitly.
- **Tests**: no strict baseline. Frame as "tests as guardrails" — accessible to first-years.
- **Starting state**: students arrive with Pi installed, a git repo, and a browser-running project they vibe-coded without reading. Most of them **will not have a test runner** — see the note in the tests block.
- **Starting state is uneven and that is expected.** Session 1's homework was open-ended ("keep going until it gets away from you"). Some will have a week of work, some nothing. The recap absorbs the variance; the exercise is written so both can do it.
- **Tooling**: **Pi**, same as Session 1, plus the Plannotator extension. Students install one thing today. See "The Pi decision" below.

## The Pi decision (read this first)

Session 2 was originally written against Claude Code — plan mode via `Shift+Tab`, plannotator as a separate web UI, `git diff` for review. The course tool is Pi. **Resolved: Session 2 runs on Pi.** Students do not install a second harness.

What that changes, concretely:

| Original (Claude Code) | Now (Pi) |
|---|---|
| Plan mode via `Shift+Tab` ×2 | `pi --plan`, or `/plannotator` / `Ctrl+Alt+P` in session |
| "Plan mode vs plannotator: same idea, two UX levels" | Collapses into one thing — see below |
| Paste the diff into plannotator's review view | `/plannotator-review` opens the working-tree diff natively |
| Subagents for plan/code review | `pi-subagents` (a package, not built in) — instructor demo only |

**The narrative gets better, not worse.** The old framing was "plan mode keeps the plan in the agent's context; plannotator externalizes it as a file — same idea, nicer UX." On Pi that distinction disappears: Pi has no built-in plan mode, so the Plannotator extension *is* plan mode, and **the plan is a file from the first moment.** There is no version of today's flow where the plan lives only in the agent's head. The session's thesis stops being a recommendation and becomes the only path available.

**Bonus content Pi gives us that Claude Code did not.** Plannotator's planning phase reconfigures the harness: it swaps the active toolset to `["grep", "find", "ls"]`, blocks destructive commands, and restricts writes to the plan file. You literally cannot execute while planning. That is worth a slide — *the harness enforces the discipline* — and it plants the permissions/extension-points seed that Diego opens in Session 3.

**One-line aside worth saying out loud**: Claude Code ships plan mode built in; Pi needs an extension. That difference is not an accident, it's the harness design space — which is Session 3. Say it and move on; don't teach it.

## Topic-by-topic plan

### Recap & debrief (~20 min) — opens the session

**This is the real reality check of the course.** Diego's in-class version at the end of Session 1 was only ~12 minutes — a first pass on 15 minutes of building, not a debrief. The material that matters was generated by the homework: *keep vibe coding with the same rules until it gets away from you, and write down when that happened.* Students were told Session 2 opens on exactly that. Open on it.

**Sync with Diego before class** — what state did students actually end Session 1 in, how many left with Pi working, what came up in his 12-minute collection. Don't re-collect what he already got.

Run it as discussion, not slides:

1. **"¿Se les fue de las manos? ¿Cuándo?"** The moment is the payload. Collect four or five, write them on the board. Expect: the agent broke something that worked, a fix that made it worse, three attempts at the same bug, a file nobody knew existed, the project got big enough that they couldn't say what it did anymore.
2. **"¿Alguien abrió el código durante la semana?"** Some will have broken the no-reading rule. That is a *good* answer — ask what made them break it. The urge to read is the instinct this whole session is built on.
3. **Cash in the predictions.** Diego presented METR (19% slower while feeling 20% faster) and the 80% problem as *predictions to check against your own experience*, before the hands-on rather than after. Now ask: was it true for you? Did the first 80% arrive fast and the rest cost more than the whole thing looked like it would? Don't argue with students who say they were genuinely faster — for a week-one prototype they probably were. That is the honest version of the finding and it makes the rest of the course credible.
4. **Name comprehension debt again.** Diego planted the term in Session 1. Today it gets its mechanism: the bottleneck moved from *writing* code to *verifying* it. Everything in this session is a way to pay that debt down.

Then the turn into the session: *"Hoy no vamos a escribir menos código. Vamos a saber qué código escribimos."*

### Git with AI (~5 min) — opens the theory block

Foundation first: before we walk through the planning/review flow, set the safety net. Frame as a **spectrum tied to context**, not a rigid workflow:

- **Solo on your own repo**: working on `main` is fine.
- **In a team**: branches per feature.
- **Parallel work**: worktrees.

Key principle: AI doesn't change git; it just makes "throw the branch away" cheaper. **Diff review is the gate before merging** — explicitly teach reading diffs critically (does it match the plan? unused code? security smells?).

Putting this first sets the explicit expectation: "everything that follows assumes you have a way to back out." It also matters more than usual today, because the hands-on has students executing an agent-written plan step by step — they need to know they can throw it away.

### Planning: the plan is a file (~15 min)

Framing: **the plan always exists. The only question is whether you can read it.** When you prompt an agent cold, it plans anyway — silently, inside its own context, and you find out what it decided by looking at the damage. Externalizing costs a few minutes and makes the plan reviewable, annotatable, versionable, shareable.

**Setup**: `pi install npm:@plannotator/pi-extension`, then `pi --plan` (or `/plannotator` / `Ctrl+Alt+P` mid-session).

**Demo flow (~7 min), on the instructor's project:**

1. Enter plan mode. **Point at the status label (`⏸ plan`) and at what just happened to the toolset** — read/search only, no writes except the plan file, destructive commands blocked. "The harness is holding me to it. I couldn't skip ahead if I wanted to."
2. Describe a feature. Let the agent explore the codebase and write the plan as a markdown checklist.
3. It calls `plannotator_submit_plan` → the browser UI opens.
4. **Deny with annotations at least once.** This is the beat that matters — do not approve on the first pass, even if the plan is fine. Annotate a vague step, a decision two people would implement differently, a missing step. Send it back.
5. Resubmission shows **Plan Diff** — what changed since the last version. Show it.
6. Approve → the agent executes with full tools restored.

**What to narrate while it runs**: the plan is a file on disk at a path you chose; you can commit it, you can hand it to a classmate, you can read it in a year. That is the whole point.

**Subagents for plan review** (subtopic, ~1 min): you can delegate the plan review itself — an agent whose only job is to read the plan and report what's vague, what's missing, where two engineers would diverge. On Pi this is a package (`pi-subagents`), not a built-in. **Mention it, don't install it** — full treatment is Session 3 (Diego).

No need to introduce decomposition as a separate topic — the plan output is already a checklist. Point at the plan's structure and say "this is decomposition" rather than teaching a rubric.

### Review: the spectrum of surfaces (~10 min)

Don't give students a checklist — show the **spectrum of review surfaces**, and be explicit that the right one depends on the size of the change and how much you trust it:

1. **Watch + steer**: review happens *during* generation. Stop the agent mid-stream, redirect. Cheapest, catches wrong direction early, misses detail.
2. **Read in editor**: open the changed files. Most direct; doesn't scale past a few files.
3. **Diff tool**: `git diff`, or [hunk](https://github.com/anthropics/hunk) for interactive hunk-by-hunk review. When the change is big, the diff gives you the shape.
4. **`/plannotator-review`**: opens the working-tree changes in the review UI. Annotate specific lines, submit the feedback straight back to the agent. Useful when you want the review to *become the next instruction* instead of just accept/reject. **Demo this on the diff the plan just produced** — same feature, closing the loop from the planning demo.
5. **Subagent for code review** (subtopic, ~1 min): delegate the diff read to an agent that reports issues, smells, divergences from the plan. Same "you can delegate this" idea as plan review, applied to the output side. Quick mention; depth in Session 3.
6. **Annai** (instructor's own in-progress tool — `案内`, "guidance"): mid-session interactive review surface that streams events between agent and reviewer, submits to GitHub via GraphQL. Mention as a contrast to plannotator's blocking model. v0.2 in design.

**The through-line to say explicitly**: the plan you approved is the spec you review the diff against. "Does this match the plan?" is a question you can only ask because you wrote the plan down.

### Task decomposition (~integrated, no separate block)

Not a standalone topic. The plan from the demo is already decomposed — that's the argument. Walk it with an "entrypoint" style: start at the main file the plan touches, branch out. Frame as "decomposition is reading flow, not a rubric — it depends on the project shape."

### Tests as guardrails (~5 min)

Framework-agnostic. Position: **"tests are the spec the AI can't game."** If you ask for behavior X and the AI writes both the code and the test claiming X works, you can still be fooled — it can weaken the assertion until it passes. If *you* wrote the assertion first, it has to satisfy it.

Skip strict TDD discipline. The win is "a test exists and you wrote it before the implementation," not red→green→refactor.

> **Reality to handle out loud**: almost nobody will have a test runner. They vibe-coded for a week without reading anything. Don't let this eat the hands-on — **delegating the runner setup to the agent is fine and correct**; it's mechanical. What the student must not delegate is the assertion. Say it that way: *"que te lo instale el agente; el `expect` lo escribís vos."*

### Debugging AI-generated code

**No theory block.** Cover organically during hands-on when things break. Instructor and TAs walk the room. The lesson is "read the code yourself before asking the AI to fix it" — and today, unlike last week, they're allowed to.

### Security sidebar (~30 sec, woven)

During the review demo, point at one concrete security smell in the diff (unsanitized input, exposed secret, missing auth check). Don't lecture. The point is to make students notice these *while reviewing*, not as a separate topic. Session 1's reality check probably surfaced real examples from the room — reuse one if it's still fresh.

## Hands-on (~50 min)

Six steps in `exercise/README.md`. Walk the room. The thing to enforce is **step 3: make them deny the plan at least once.** Students will approve the first plan out of politeness to the machine. That skips the entire lesson.

Other things to watch for:

- Feature scope. Anyone who picks something touching 5+ files will not finish. Cut them down early, in the first five minutes.
- The plannotator install. It's one command, but it's the only setup today and it's on the critical path.
- Students who skip the test because "it's faster." That's true and that's the point — ask them at the end whether they'd have caught the bug without it.

## Session timing (~2 h)

| Block | Time |
|---|---|
| Recap & debrief from Session 1 | 20 min |
| Theory: git with AI | 5 min |
| Theory: planning — the plan is a file (+ live demo) | 15 min |
| Theory: review surfaces (+ `/plannotator-review` demo) | 10 min |
| Theory: tests as guardrails | 5 min |
| Break | 5 min |
| **Hands-on** | **50 min** |
| Closing: discussion + what's next | 10 min |

Adds to ~110 min, leaving ~10 of slack. **If it runs long, cut from the recap** (it's the most elastic block) — not from the hands-on, and never from the diff review at the end of it, which is where the session lands.

## What we explicitly skipped (and why)

- **LIDR borrowings** (Decision Closure Rule, Verification tiers): too enterprise-flavored for this audience.
- **Code review checklist**: replaced with "spectrum of review surfaces" — strategies, not a rubric.
- **Dedicated debugging block**: covered organically in hands-on.
- **Claude Code as a second harness**: considered and rejected — one tool, one project, six sessions. The built-in-vs-extension difference gets one sentence as a Session 3 bridge.
- **Plannotator's config layers** (`plannotator.json`, per-phase models, `executionMode`): real, and irrelevant to a first exposure. Skip unless a student asks.
- **Closing security prompt**: 30-second mention in the demo is enough.

## Open items (for future iterations)

- **Pick the instructor's demo project** — what codebase do you actually run plan mode on? It has to have enough shape that a plan is non-trivial, and be safe to show on a projector.
